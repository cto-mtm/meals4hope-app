# Translations Cookbook

vue-i18n in Composition API mode (`legacy: false`). **Spanish (`es`) is the primary authored locale**; English (`en`) is the fallback. Setup lives in `src/i18n/index.ts`.

Strings live in **per-feature TypeScript modules**, not monolithic JSON. Each module co-locates both locales and types `en` against `es`, so a missing or extra key in either language is a **compile-time error** — not a runtime warning.

## Structure

```
src/i18n/
├── index.ts                 # assembles modules, builds messages, type augmentation
└── locales/
    ├── configs/             # cross-cutting vocab (common)
    ├── components/          # component-scoped strings (shell, facturas, attachments, audit, contacts)
    └── pages/               # page-scoped strings (login, dashboard, entradas, salidas, partners, admin, notFound)
```

The folder is organizational only. Each module registers under its **namespace key** (the file name), so keys stay `t('entradas.title')` regardless of folder.

## Module format

```ts
const es = {
  title: 'Entradas',
  empty: 'Sin entradas',
}

// Typed against es: a missing or extra key here is a compile error.
const en: typeof es = {
  title: 'Inflows',
  empty: 'No inflows',
}

export default { es, en }
```

## 1. Add a translated string

1. Open the module for that feature (e.g. `locales/pages/entradas.ts`).
2. Add the key to **both** `es` and `en` in the same edit. If you forget one, `tsc` fails on `en: typeof es`.
3. In the component: `const { t } = useI18n()` then `t('entradas.key')`. Keys autocomplete from the schema.

Never options-API `$t` in script, never a hardcoded user-facing string in a template or store.

> Type-safety note: `en`↔`es` key parity is enforced at compile time, and key autocompletion works via the `DefineLocaleMessage` augmentation in `index.ts`. However, vue-i18n keeps a permissive `t(key: string)` overload, so an outright typo in a `t()` call is *not* a `tsc` error — the missing-key console warning in dev is the backstop.

## 2. Add a new namespace

1. Create `locales/<folder>/<name>.ts` exporting `{ es, en }` in the format above.
2. In `index.ts`, import it and add one line to each of the `es` and `en` blocks of `messages`. (If the name collides with a JS reserved word, alias the import binding but keep the registered key unchanged.)

## 3. Add a new locale

1. For every module, add the new locale typed against `es` (`const fr: typeof es = { … }`) and include it in the export.
2. Add the code to `SUPPORTED_LOCALES` and the `messages` + `datetimeFormats` blocks in `index.ts`.

## 4. Translate data (not just UI chrome)

App-owned enums render through keys: estados via `t('common.estados.' + value)` (see `EstadoChip.vue`), partner types via `t('partners.types.' + type)`, roles via `t('admin.roles.' + role)`. Catalog entries (áreas, líneas) and everything typed by users are **data, not UI** — they are stored and shown as-is, never translated.

## 5. Dates, numbers, currency

Use `d(date, 'short')` from `useI18n()` for timestamps — never hand-format. Money renders through `formatMoney()` in `src/lib/money.ts` (Intl-based, per-currency). Times are stored UTC and rendered local; date-only fields are plain `YYYY-MM-DD` strings. Careful with `@` inside messages — vue-i18n treats it as linked-message syntax, so escape it as `{'@'}`.

## The rules

Every user-facing string is a key in a per-feature module, present in both `es` and `en`, same commit, enforced by the type system. Data stays translatable via keys where app-owned. `LocaleSwitcher.vue` (in the header) flips the global locale.
